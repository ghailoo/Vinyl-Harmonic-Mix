# Apple design audit — VinylHarmonicMix (macOS)
Date: 2026-10-12 · Against developer.apple.com/design/resources + current HIG (app-icons)
Note: the audit tooling is written for iOS. macOS-irrelevant rules (44pt touch targets, tab bars, simulator runs) were skipped.

## Findings, ranked

### 1. 🔴 The app has no icon
`Assets.xcassets/AppIcon.appiconset/` contains only `Contents.json` — zero image files. The app ships with the
generic blank macOS icon. There is also no Icon Composer `.icon` file.

HIG (app-icons): "Although you can provide a flattened image for your icon, layers give you the most control…
iOS, iPadOS, macOS, and watchOS app icons include a background layer and one or more foreground layers that
coalesce to create dimensionality. These icons take on Liquid Glass attributes like specular highlights,
refraction, and translucency."

Fix: design the icon in Icon Composer (free, on the design resources page) and ship a layered `.icon` with
default / dark / clear / tinted. Effort: a few hours including artwork.

### 2. 🟠 No privacy manifest
No `PrivacyInfo.xcprivacy`, while UserDefaults/@AppStorage is used in 11 files.
Required for App Store submission; not required for direct DMG distribution. Conditional on how you ship.
Effort: ~30 min.

### 3. 🟠 Colours still don't adapt to dark mode
25 `Color(red:green:blue:)` literals and 12 hardcoded `.white`/`.black` foregrounds. These were flagged in the
earlier audit and that work was never done. Fixed RGB can't adapt, so dark-mode contrast is accidental.
Fix: semantic colour tokens in the asset catalog with light/dark variants; verify 4.5:1 in both. Effort: half a day.

### 4. 🟡 Dynamic Type only partly adopted
435 semantic text styles (good — this was 207 hardcoded sizes before), but 4 fixed `.system(size:)` remain and
there are zero uses of `@ScaledMetric` or `dynamicTypeSize`. Semantic styles scale on their own, so this is
mostly fine; the gap is fixed-height rows that won't grow with the text.

**Status: NOT APPLICABLE on macOS.** macOS has no system Dynamic Type for SwiftUI — the Accessibility
"Text size" setting only reaches some Apple apps. Tested on macOS 27.0.1: a view with `.body` and `.largeTitle`
text plus a 100pt `@ScaledMetric`, rendered at `.dynamicTypeSize(.large)` and `.accessibility5` via both
`ImageRenderer` and `NSHostingView`, gave identical sizes (100×67pt) — text did not grow, `@ScaledMetric` stayed
100, layout delta 0pt. So `@ScaledMetric` would be a no-op and nothing clips at larger sizes. The "4" fixed
sizes are really 3 (`Tokens.swift:21–25`, documented tokens `statValue`/`iconLarge`/`iconHero`); the fourth hit
is the "Never hardcode" comment on `Tokens.swift:6`. No code changes.

### 5. 🟡 Small hit targets
22×22pt buttons at SetBuilderView.swift:628, 700, 705, 710 — only :628 uses the existing `.hitTarget()` helper.
30×30 at CollectionDetailView.swift:214 (artwork carousel arrows). macOS has no 44pt rule, but ~28pt is the
practical floor for a pointer. The helper already exists; it just isn't applied. Effort: 15 min.

### 6. 🟡 Dead iOS configuration
`SUPPORTED_PLATFORMS = "iphoneos iphonesimulator macosx"` and `IPHONEOS_DEPLOYMENT_TARGET = 26.5`, while the app
is macOS-only in practice (`MACOSX_DEPLOYMENT_TARGET = 15.0`). The iOS branch in ContentView is maintained for a
platform you don't ship. Either drop iOS from the target or state the intention.

## Already compliant
- SF Symbols used throughout; no emoji as icons
- 435 semantic text styles; one shared type scale (Tokens.swift)
- Materials used for chrome (toolbars, sheets), not content
- 48 `.accessibilityLabel` matching 48 `.help()` tooltips
- Reduced-motion handling in the animated views
- Undo for destructive set actions; confirmation for data reset
- No permission-requiring frameworks, so no missing usage strings
